# P6 与 ai-agent-book 第 7 章的对齐

依据：`book/chapter7.md`（《深入理解 AI Agent：设计原理与工程实践》第 7 章 · Agent 的评估）。
本文件是 P6 的设计基准，取代此前版本化的 P6 设想。

## 结论

第 7 章覆盖 coding agent，且对 coding 场景的表述比对人机交互场景更具体、更可执行。
但**不能整体平移**，因为第 7 章自己把评估环境分成两型：

> 人机交互型与工具调用型评估环境

coding agent 属**工具调用型**。书中 telecom 案例的模拟用户、耐心耗尽、`###STOP###` 属于人机交互型。

**架构定调（对我们最重要的一句）**：

> 凡是能写成程序化断言的检查都应当继续用断言，LLM 评判只用于确实无法机械判定的维度。
> 确定性检查更便宜、更稳定，也更适合作为回归测试长期运行。

因此 P6 是 **verifier-first**，不是 judge-first。Rubric 与 Judge 只覆盖不可机械判定的维度。

## 一、直接对齐（第 7 章点名 coding 场景）

### 1. 双命题验证器 —— 这就是 V01 的正确实现

> SWE-bench Verified 将"修复完成"拆解为两个独立命题。一组是 FAIL_TO_PASS：修复前失败、
> 修复后通过，证明问题确已解决；另一组是 PASS_TO_PASS：修复前后均通过，证明未引入新的
> 缺陷。只检验前者，Agent 可以通过删改妨碍通过的断言蒙混；只检验后者，则等同于未作检验。
> 它还额外确认测试自身的稳定性，排除时而通过时而失败的不稳定测试（flaky test）。

两个推论：
- 单查一侧**在原理上就不成立**，所以 V01 不能用"有没有改测试"这类启发式代替严格做法。
- flaky 排除是验证器自身的要求，不是可选的质量提升。

### 2. 失败归因的 coding 七类 → 每类对应的回归任务构造

> 以 Coding Agent 为例，流程缺失应生成带有计划文档和测试验收条件的端到端回归任务；
> 工具调用错误应把出错前缀截断并编辑成边界任务，测试模型能否修正格式、转义特殊字符或
> 换用合适工具；执行异常应加入截断、超时和工具故障的恢复场景；完成度与逻辑错误则应加入
> 多目标清单、剩余任务提醒和"尚未证明不可能"的边界；需求理解与歧义类应把有多种合理解释
> 的任务冻结成前缀，把"先澄清"列入可接受动作；症状修复与验证造假类则应在验收里补上
> "不得修改测试断言"和"完成声明必须附带真实执行过的命令输出"两条硬约束；信息反馈类应在
> 验收里对答复内容本身设断言，而不只检查环境状态。

归因对象是**首个导致任务偏离的错误**，不是最后一个报错：

> 归因对象是轨迹中的首个导致任务偏离的错误，后续错误往往只是连锁反应，
> 不能把最后一个报错简单当成根因。

### 3. 轨迹前缀回归任务（第 7 章称其"往往比端到端更重要"）

> 轨迹前缀（trajectory prefix）回归任务则截取首个错误之前的状态，只验证那个决策边界是否被修好。
> 轨迹前缀回归任务的答案应定义为可接受动作集合，而不是唯一的动作或答案：可以要求
> "先读仓库规则""先询问用户"或"拒绝危险操作"，同时列出禁止动作。

实验 7-7 的边界用例本身就是 coding 味的：worktree/PR 习惯与仓库规则冲突、
当前明确指令覆盖旧偏好、高风险删除前确认、对外发布前预览。

### 4. 证据不可伪造

> Agent 很容易写一篇洋洋洒洒的报告，说任务已经全部完成，但事实上根本没有完成。
> 评估框架必须核实机器可独立复核的事实，而非 Agent 的自我陈述。

Terminal-Bench 的 `build-linux-kernel-qemu` 是范例：成功标准是启动日志中出现自定义 printk，
"Agent 无法伪造输出，只能真正完成整个流程"。

### 5. 指标与统计（已实现）

`Pass@k = 1-(1-p)^k`、`Pass^k = p^k`、`SE ≈ sqrt(p(1-p)/n)`、配对分析（McNemar / 配对 bootstrap）、
3–5 个种子报均值与波动。已落地于 `src/run_agent_evals/statistics.py`，
测试锚定书中算例（0.6/k=5 → 99.0% 与 7.8%；100 题 70% → ±9pp）。

**利好**：第 7 章要求有副作用的操作"应在沙盒或可回滚环境中采样，并把每一次失败都记入可靠性指标"。
我们 P2 的事务化快照 + 回滚已经在做这件事，所以 `Pass^k` 在本项目是**真实测量**而非估算。

## 二、需改形（第 7 章的五要素 → coding 版）

| 五要素 | 书中 telecom 形态 | coding agent 形态 |
|---|---|---|
| Dataset | 工单 + 模拟器行为规范 | 初始**仓库快照** + issue + 验收条件 |
| Environment State | 数据库 + 设备开关；`initialization_actions` 重置 | **git 仓库状态**；用已有 snapshot/rollback 重置 |
| Tools | 运营商侧 + 用户侧两套原子操作 | 已有的原子工具（read/write/bash…）；**不得出现"修好这个 bug"式高层抽象** |
| Rubric | `evaluation_criteria` 四层检查 + `reward_basis` | 验收标准 + 聚合规则；**仅用于不可机械判定维度** |
| Interaction Protocol | `###STOP###`、模拟用户耐心耗尽 | **终止条件**：完成 / 取消 / 预算耗尽 / 轮数上限 |

第 7 章对工具原子性的理由是直接的：

> 抽象层次过高会使评估退化为对单次函数调用的考察，规划与推理环节被工具本身吸收。

## 三、不适用（避免过度建设）

| 第 7 章内容 | 不适用理由 |
|---|---|
| 模拟用户 / `###STOP###` | 人机交互型专用 |
| 多源异构评判 | 成本高；coding 判定大多确定性，仅在 Judge 尾巴上按需使用 |
| Elo 评分 / 模型排名 | 我们评估的是**本项目 harness 自身改动**，不是给外部模型排名；配对比较才是所需 |
| GAIA 三级难度、数据泄漏金丝雀 | 面向公开基准防泄漏；自建集不涉 |

## 五、P6 结构（verifier-first）

```
确定性验证器（FAIL_TO_PASS + PASS_TO_PASS + flaky 排除）   ← 主体，先做
  └─ 轨迹前缀回归任务（可接受动作集合 + 禁止动作）          ← 高可靠场景优先
      └─ 失败归因（首错 + 七类 + 证据）→ 回流成新任务
          └─ Rubric(加权 + veto) + LLM-as-a-Judge          ← 仅不可机械判定维度
              └─ Pass@k / Pass^k / SE / 配对比较 → 决策
```

据此调整任务顺序：双命题验证器与轨迹前缀**前置于** Rubric 与 Judge。
