# Session extensions

A Session extension is a Python module exporting synchronous `setup(api)`. Explicit files load with `run --extension <path>`; user extensions live under `~/.run/extensions`. Project extension discovery requires `--project-extensions` and the configured project trust decision.

```python
def setup(api):
    api.add_prompt_guideline("Follow the repository's existing conventions.")

    def started(event, context):
        context.ui.set_status("mode", "Project assistant")

    api.on("session_start", started)
```

Register tools with `api.register_tool(tool)`, commands with `api.register_command(...)`, and hooks with `api.on(event_name, handler)`. `api.on` accepts Pi's 36 event names (21 observation + 15 hooks). Existing hooks include `input`, `before_agent_start`, `context`, tool call/result hooks, `message_end`, `session_start`, `session_shutdown`, and the other Pi session/provider events. See `run_agent_coding/extensions/api.py` for exact payload types. `session_before_compact` is emitted by the extension that owns compaction (`compaction`) through `context.request_session_before_compact(...)` once the commit attempt is certain - all preconditions for producing the summary hold - and always before the summary model call; a handler that cancels skips that compaction for the request (and saves the summarizer call), while the free view rewrites already applied stay. The call returns a `SessionBeforeCompactDecision`: `cancelled` is the veto, and `context` is every handler's non-empty `SessionBeforeCompactResult.context`, blank-line separated - free text (for example a memory provider's pre-compression insight) that the caller uses as summary material, never as an instruction.

`agent_settled` is emitted after final session entries and execution outcome commit. It carries `run_id`, `session_id`, `branch_id`, `status`, `head_id` and `watermark`. `agent_end` marks the model/tool loop boundary and does not itself prove a durable final result. A failed completion transaction does not emit `agent_settled`.

The UI contract is textual:

- `context.ui.notify(text)` displays a notification.
- `await context.ui.select(title, options)` returns a selection or `None`.
- `await context.ui.confirm(title, message)` returns true only after confirmation.
- `await context.ui.input(title, secret=False)` returns text or `None`; secret input is hidden and does not enter terminal history.
- `context.ui.set_status(key, text)` updates an extension-owned status line; passing `None` removes it.

Headless hosts return `None` or false for dialogs. Extensions must not treat unavailable confirmation as approval. Extensions cannot mount terminal widgets or intercept keys.

Registration failures remove source-owned registrations. Reload and session replacement stage a successor without touching the live runtime. Only after host publication commits does the old generation enter a read-only retiring phase, receive shutdown notification, clear its status, and drain source-owned disposers in reverse order. Captured APIs from a retiring or retired generation reject mutations. This is lifecycle management, not an operating-system sandbox; trusted Python extensions can still perform direct effects the host cannot reverse.

All seven built-ins in `run_agent_extensions` load by default in new CLI sessions: `experience`, `memory`, `compaction`, `curator`, `mcp`, `permission_policy` and `plan_mode`. Plan mode starts off. Permission uses `RUN_AGENT_PERMISSION_MODE` (`review` default, `yolo`/`autonomous`, `strict`) and does not register tools. MCP reads `<cwd>/.mcp.json`, connects on `session_start`, and releases connections through a source-owned disposer. `--no-extensions` disables default and discovered extensions; explicit `run --extension <name-or-path>` entries still load without duplicates. Saved sessions retain their extension snapshot until `--refresh-resources` adopts current defaults. Event tracing is a session option (`--trace`, `/trace`) rather than an extension.

`inference.complete` accepts existing tool schemas by name and returns proposed calls without executing them or altering the main transcript. `evaluation` is host-owned: it is unavailable by default and never treats missing evidence as success.

Experience owns verifier-gated Skill evolution only: formal Skills are read-only to the model, and `skill_manage propose` creates an isolated cold candidate bound to a committed run, base digest, bounded edit operations and optional project probes. A candidate enters the normal Skill loader only after the host evaluator measures the frozen candidate and `/evolve publish` rechecks the report, probes, ownership, pin and base digest. Experience itself has no cadence-driven writeback, archive or consolidation pass: that maintenance loop belongs to the `curator` built-in below, which never edits Skill content. See `run_agent_extensions/experience/README.md` for the exact gate.

`memory` (`run_agent_extensions/hermes_memory`, ported from hermes-agent) owns long-term memory: it keeps `USER.md` (user scope, `~/.run/USER.md`) and `MEMORY.md` (project scope, `<cwd>/.run/MEMORY.md`) as budgeted, threat-scanned Markdown entries, and registers the `memory` tool plus `/memory show|add|replace|remove [--scope]`. Its hooks are `session_start` (resolve scopes, load both files, freeze the snapshot), `before_agent_start` (append the cached `# Long-term memory` section), `input`/`turn_start`/`agent_settled` (per-turn budget, recall prefetch and provider sync), `context` (one request-local `<memory-context>` message; session history is never rewritten), `session_before_compact` (returns `on_pre_compress(transcript)` as the gate's `context`, which the `compaction` extension fences into its summary prompt as material; nothing is kept for the next request), `session_before_switch` and `session_shutdown` (ordered boundary commit and a bounded drain). Writes are durable immediately; the prompt keeps the frozen snapshot until the next session or `/reload`.

`compaction` (`run_agent_extensions/layered_compaction`) owns compression, and loading it is what gives a session compaction: it runs the cheap-first pipeline in `before_provider_request` - a token gate at 80% of the budget (below it *no layer runs at all*), then the three free layers as one batch (L1 persists oversized tool results to `<cwd>/.run/tool-results/<tool_call_id>.txt` with an atomic replace, L2 snips the middle of a view longer than 50 messages, L3 placeholders old tool results), and only a view that is still over the gate gets one L4 model summary (bounded inference, user-boundary tail) - and it requests at most one durable commit per request. Layer numbers are the execution order; the reference implementation this strategy comes from numbers the same three free strategies `L3`/`L1`/`L2` and the summary `L4`. Memory is not a layer of it: a memory file is never reused as a summary; the memory extension's `on_pre_compress` text reaches the summarizer prompt only as fenced material under `<memory-provider-context>`, carried by the `session_before_compact` gate. It fires that gate itself (`context.request_session_before_compact`) only when a commit attempt is actually going to run - a provider is available, the split point is legal, the breaker is not tripped - and always before the summary model call, so a handler can veto that compaction without paying for the summary; a veto keeps the free rewrites, commits nothing and warns through the UI. The compaction extension also exposes the session's effective context window (`context.context_window_tokens`, the same value the hard guard uses) and takes its budget from `min(that window, COMPACTION_LAYER_CONTEXT_WINDOW)` when the variable is set. It registers `/compact [instructions]` (the `snip` tool and `/force-snip` were removed with the strategy change) and one prompt guideline naming the persisted-output path. Its own configuration (`COMPACTION_LAYER_ENABLED` and the per-layer switches) is the only switch; the core applies no compaction of its own, so without the extension a request is never rewritten and an over-window one is refused by the hard guard.

`curator` (`run_agent_extensions/curator`) is the maintenance half of the Skill system: it never writes a Skill body, and any content change it proposes still has to pass the experience gate (`SkillEvolution.propose` → candidate → host report → `/evolve publish`). Its hooks are deliberately cheap: `session_start` runs the cadence gate (`CURATOR_INTERVAL_HOURS`, default 168) and only seeds `last_run_at` on the first session; a due pass snapshots every Skill root, marks inactive Skills `stale`, archives unprotected evolution-owned Skills into `<skills-root>/.archive/` (never deletes) and runs one bounded review. `agent_settled` only records the source run for later candidates, `input`/`tool_call` record `/skill:<name>` and `skill_manage(action=view)` consultations in `usage.jsonl`, and `session_shutdown` flushes `state.json` under `<extension_state_dir>/curator/`. Its `/curator status|run [--dry-run]|pause|resume|restore|report|review|learn|journey ...` commands are host commands, not tool calls: they bypass the permission and plan-mode tool gates, so each destructive action asks `context.ui.confirm` and is refused without a UI.
